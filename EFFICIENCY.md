# VeriMon efficiency study: refinement hypothesis and verified code optimizations

This document records an investigation into why VeriMon (the verified kernel, `-verified`)
is slower than MonPoly (the unverified kernel sharing the same binary), a quantitative test
of the hypothesis that refining the formalization to Imperative HOL or LLVM would close the
gap, and the verified optimizations implemented on this branch (`refine`).

All measurements were taken on the same machine (4 cores, OCaml 4.14.1 without flambda,
`dune build --profile=release`), single-threaded, wall-clock, best of one run (noise < 5%).

## 1. Baseline: where does VeriMon spend its time?

### 1.1 Benchmarks

* `P2`, `P3`: the CAV'10 policies shipped in `examples/mfotl`, with logs produced by
  `tools/gen_log` (`-event_rate 2000 -time_span 100`, about 200k events).
* Synthetic formulas over the signature `A(int,int) B(int,int) C(int)` with a log of 2000
  time points, 50 `A`- and 50 `B`-tuples and 13 `C`-tuples per time point drawn from a domain
  of 200 values (`evaluation/synthetic/gen_log.py 2000 50 200 log.log`, formulas in the same directory):

  | name | formula |
  |---|---|
  | and | `A(x,y) AND B(y,z)` |
  | andnot | `A(x,y) AND NOT B(x,y)` |
  | once | `ONCE[0,20] A(x,y)` |
  | since | `B(x,y) SINCE[0,50] A(x,y)` |
  | eventually | `EVENTUALLY[0,10] A(x,y)` |
  | until | `A(x,y) UNTIL[0,20] B(x,y)` |
  | agg | `s <- SUM y; x A(x,y)` |
  | complex | `A(x,y) AND (ONCE[0,20] B(y,z)) AND NOT C(z)` |

Baseline timings (MonPoly vs. VeriMon before this branch; outputs are identical):

| formula | MonPoly | VeriMon (old) | ratio |
|---|---|---|---|
| P2 | 0.44 s | 2.83 s | 6.4x |
| P3 | 0.45 s | 2.64 s | 5.9x |
| and | 0.17 s | 0.79 s | 4.6x |
| andnot | 0.18 s | 0.76 s | 4.2x |
| once | 0.78 s | 3.30 s | 4.2x |
| since | 0.29 s | 1.01 s | 3.5x |
| eventually | 0.49 s | 1.74 s | 3.6x |
| until | 0.26 s | 0.60 s | 2.3x |
| agg | 0.17 s | 0.49 s | 2.9x |
| complex | 0.99 s | 8.85 s | 8.9x |

Parsing the 2 MB synthetic log alone costs about 0.08 s (MonPoly) / 0.19 s (VeriMon, which
additionally converts every tuple into the verified `event_data option list` representation
and inserts it into an RBT-based database).

### 1.2 Profiles (`perf record`, `--call-graph dwarf`)

The profiles of the old VeriMon are flat: no single monitor operation dominates. Aggregated
over `P2`, `P3`, `and`, `complex`:

* 20-30% garbage collection (`do_some_marking`, `caml_oldify_*`, `bf_allocate`, ...),
  i.e. allocation pressure from persistent data structures and short-lived closures;
* 12-25% comparator dispatch: `comparator_of` (which performs *two* dictionary-dispatched
  comparisons, `<` and then `=`, per element), `comparator_list`, `comparator_option`,
  `comparator_event_data`, `compare_nat`, `caml_apply2` (unknown function calls through
  closures);
* 8-12% *construction* of type-class dictionaries at run time (`ccompare_lista`,
  `ccompare_optiona`, `ceq_lista`, `ceq_seta`, ...). Every polymorphic function generated by
  Isabelle's code generator rebuilds the `ccompare`/`ceq` records for `event_data option list`
  on every call, e.g. once per inserted tuple inside a fold;
* 10-25% red-black-tree operations proper (`rbt_comp_ins`, `balance`, `rbt_comp_lookup`);
* 3-5% arbitrary-precision arithmetic on `nat` (`Z.add`, `ml_z_compare`, `suc`, ...).

Inclusive attribution to monitor operations:

* `P2` (Until): 62% in `add_new_mmuaux` (the Until auxiliary structure), of which 26% in
  `eval_step_mmuaux`; the rest is buffering, database construction and output conversion.
* `P3` (Since): 56% in `meeval_since` (`add_new_ts_mmsaux` 20%, `shift_end` 14%,
  `gc_join_mmsaux` 10%, `add_new_table_mmsaux` 9%), 7% multi-way join.
* `and`, `complex` (joins): 58-65% in `New_max_getIJ_genericJoin`, the worst-case optimal
  multi-way join, which repeatedly projects and intersects tables (`projectTable`,
  `inf_seta`, `image`) and builds many intermediate RBT sets. The binary nested-loop join
  (`-no_mw`) is even slower on `complex` (21.6 s).

## 2. Testing the refinement hypothesis

The hypothesis was that refining the algorithm to Imperative HOL (mutable arrays, hash
tables) or to LLVM (via Isabelle-LLVM) would make VeriMon competitive.

### 2.1 A direct data point: MonPoly's Since/Until

MonPoly's `src/optimized_mtl.ml` is an *imperative* OCaml port of exactly VeriMon's
`mmsaux`/`mmuaux` algorithms (`Optimized_Since.thy`, `Optimized_Until.thy`), using
`Hashtbl` for the tuple-indexed mappings and mutable queues. On `P3`/`since`/`P2` it is
3.5-6x faster than the generated code. This upper-bounds what "the same algorithm,
imperative, hand-written" can gain, but it conflates several effects.

### 2.2 Decomposing the gap with a microbenchmark

`evaluation/microbench/micro.ml` (`dune build evaluation/microbench/micro.exe`) inserts 300k random binary tuples into a set
and then performs 300k membership tests, using the generated code and hand-written OCaml on
the *same* data:

| implementation | time |
|---|---|
| (a) generated `RBT_set` insert/member, dictionaries rebuilt per call (as in generated polymorphic code) | 1.81 s |
| (a') generated `RBT_set`, dictionaries built once | 1.49 s |
| (b) `Set.Make` (AVL) on `event_data option list` with a direct hand-written comparator | 0.85 s |
| (c) `Set.Make` on `Z.t list` with polymorphic compare (MonPoly's representation) | 0.80 s |
| (c') `Set.Make` on `int list` with polymorphic compare | 0.76 s |
| (d) `Hashtbl` on `event_data option list` | 0.36 s |
| generated `inf_set` (RBT intersection), 20 x 150k | 2.32 s |
| `Set.Make.inter`, 20 x 150k | 1.17 s |

Conclusions:

1. The tuple representation (`event_data option list` vs. `cst list`) is irrelevant
   ((b) vs. (c) vs. (c')).
2. Dictionary passing and generic comparator dispatch cost about **2x** ((a) vs. (b)):
   1.2x for rebuilding dictionaries, 1.7x for the comparator call chain
   `comparator_list -> comparator_option -> comparator_event_data -> comparator_of ->
   less/eq` through closures and dictionary records.
3. Persistent balanced trees vs. an ephemeral hash table cost another **2.3x** ((b) vs. (d)).
4. The product (about 5x) matches the observed gap for the Since/Until-dominated
   benchmarks. For join-dominated benchmarks the additional factor is algorithmic (Section 1.2).

### 2.3 Assessment of Imperative HOL and LLVM refinement

* **Imperative HOL** would address item 3 only. It does not remove dictionary passing: the
  Imperative HOL collections (hash maps in the Separation Logic / Refinement Framework
  libraries) are themselves generic in `hashable`/`equal` dictionaries and would generate the
  same kind of code, and the `Heap` monad is compiled to OCaml as thunks
  (`unit -> 'a`), adding a closure allocation per bind. The expected gain is therefore bounded
  by roughly 2x on set/map heavy operations (perhaps 1.5x end-to-end by Amdahl's law), for a
  very large proof effort: `'a table = 'a tuple set` is the interface of all optimized
  theories (`Optimized_Since/Until/Trigger/Agg*`, about 20k lines of proof) and the monitor
  state is a purely functional value that is threaded, copied (e.g. `MLet`/`MFrz`
  snapshots) and compared; every use site would need a refinement relation and a
  separation-logic invariant.
* **Isabelle-LLVM** would additionally require reimplementing all containers, strings,
  arbitrary-precision integers and doubles in LLVM with manual memory management proofs, and
  a foreign-function marshalling layer between the OCaml front end (parser, MonPoly
  interoperability, output) and the LLVM heap. The front end alone already accounts for
  20-30% of VeriMon's run time on these benchmarks, so the marshalling would likely eat a
  substantial part of the gain.

**Verdict:** the hypothesis is only partially supported. Imperative refinement would buy at
most a ~2x constant factor on data-structure operations, whereas the measurements show that
(i) an equal factor is lost to code-generation artefacts (dictionaries, comparators) and
(ii) the largest factors on realistic formulas are algorithmic (the generic multi-way join
and the quadratic nested-loop binary join). Both (i) and (ii) can be fixed while staying in
the pure, already verified setting, with orders of magnitude less effort. This is what the
rest of this branch does. Imperative refinement remains a sensible *follow-up* once the cheap
factors are gone.

## 3. Verified optimizations implemented (`thys/MFODL_Monitor_Devel/Code_Opt.thy`)

All changes are new *code equations* proven as unconditional theorems and registered with
`[code]`; the definitions used in the correctness proofs (`Correctness.thy`) are untouched,
and so are the proofs. The exported `src/verified.ml` was regenerated from Isabelle.

1. **Direct comparators.** Code equations for `compare :: nat/integer/string8` and for the
   derived `comparator_event_data` that perform a single `<`/`=` test on the concrete type
   instead of going through `comparator_of` and the `linorder` dictionary.
2. **Index-based binary join.** The general case of `bin_join` (neither column set contains
   the other) clusters both tables by their common columns (`cluster`, an RBT of RBTs) and
   joins only matching buckets (`mapping_join`). The code equation is unconditional because
   it checks, in linear time, that every tuple is defined on the join columns; otherwise it
   falls back to the nested loop (this never happens for well-formed tables).
3. **Nested-loop join as a fold.** The default code equation for `A ⋈ B` builds a set of
   singleton sets (which requires the expensive lexicographic comparator on *sets*) and then
   takes its union. A code equation evaluates it as a double fold inserting joined tuples
   directly (`join_True_fold_code`). This also speeds up the bucket joins of item 2.

Additionally, in `thys/MFODL_Monitor_Devel/Optimized_Join.thy`:

4. **Pairwise multi-way join.** `mmulti_join` (used for `MAnds`, i.e. all conjunctions after
   `convert_multiway`) is now *defined* as a left-deep sequence of binary joins followed by
   anti-joins for the negative conjuncts; the worst-case optimal generic join is kept as
   `mmulti_join_gen`. `mmulti_join_correct` is re-proven with the same statement plus the
   assumption that the negated conjuncts' columns are covered by the positive ones, which
   `qtable_mmulti_join` (`Correct_Bin_Ops.thy`) already had (`fv_subset`); this is the only
   change to the correctness development (one line).

   A first attempt kept the generic join as the definition and switched to the pairwise
   evaluation through an unconditional code equation guarded by a run-time check that all
   inputs are well-formed tables. That check is linear in the sizes of *all* input tables at
   every time point, while the join itself is often much cheaper (e.g. one new tuple against
   a large negated table): on `P3` it slowed VeriMon down by two orders of magnitude. Guards
   in code equations must be asymptotically dominated by the operation they guard; the
   `complete_on` check in `bin_join` (linear in the two tables that are being indexed) is fine.

## 5. Further opportunities (not implemented)

* **Dictionary hoisting / monomorphization.** 8-12% of the run time constructs type-class
  dictionaries. Isabelle's code generator has no facility to share dictionaries across calls
  of polymorphic functions; the options are (a) making the hot theories monomorphic in
  `event_data`, or (b) a post-processing pass on the generated OCaml (a MLton-style
  monomorphization). Both are mechanical but invasive.
* **Native machine integers for `nat`.** Time points and time stamps are `Z.t` big integers.
  Mapping them to 63-bit OCaml integers would be unsound without overflow checks.
* **Until auxiliary structure.** `add_new_mmuaux` dominates Until formulas; it maintains
  three nested `Mapping`s keyed by tuples and rebuilds a `tmp` set per time point. An
  algorithmic review is warranted.
* **Imperative refinement** of `mmsaux`/`mmuaux` (Section 2.3), once the above are done.
